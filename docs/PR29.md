# PR #29 릴리즈 제출 파일 검사

## 관련 Issue

- [Issue #28](https://github.com/sys-arg/arg-ubuntu/issues/28)

## 구현한 기능

### 제출 트리 검사와 빌드

- 동작 — 릴리즈 PR의 병합 후보에서 브랜치 이름과 개발 전용 테스트 경로를 검사한다. 제품 파일이 있으면 클린 빌드와 `./arg --help` 응답을 확인한다.
- 사용 기술 — GitHub Actions와 Ubuntu 24.04 러너, Git `ls-tree`로 브랜치 전체의 추적 파일 검사, GCC·GNU Make로 빌드, GNU `timeout`으로 실행 시간 제한.
- 핵심 코드 — [release-validation.yml](../.github/workflows/release-validation.yml#L23)의 경로 검사, [제품 파일 감지](../.github/workflows/release-validation.yml#L39), [빌드 및 실행](../.github/workflows/release-validation.yml#L64).

### 릴리즈 브랜치 준비

- 동작 — 최신 `main`에서 만든 릴리즈 브랜치에 테스트를 통과한 `dev` 커밋의 제출 파일을 반영하고, 병합된 `main`에 버전 태그를 생성한다.
- 사용 기술 — Git `restore`의 경로 제외와 `rm`으로 개발 전용 파일을 걸러내고, GitHub Release를 검증된 태그에서 생성한다.
- 핵심 절차 — [CONTRIBUTING.md](../CONTRIBUTING.md#릴리즈)의 릴리즈 명령과 리뷰 절차.

## 주요 변경 사항

- [AGENTS.md](../AGENTS.md)의 개발 테스트 경로·명령과 제출용 검증 기준을 명시했다.
- [CONTRIBUTING.md](../CONTRIBUTING.md)의 브랜치 규칙과 릴리즈 절차를 갱신했다.
- [release-validation.yml](../.github/workflows/release-validation.yml)을 추가했다.

## 검증 결과

- macOS에서 워크플로 YAML을 파싱하고 각 셸 단계에 `bash -n`, 변경 파일에 `git diff --check`를 실행했다.
- 임시 Git 저장소에서 테스트가 없는 초기 트리 통과, 직접 `dev` PR, C·Python 테스트와 개발 워크플로 유입, Makefile 누락, 도움말 출력 누락의 실패를 확인했다.
- 같은 임시 저장소에서 두 버전의 릴리즈 명령을 재현했다. 제품 파일의 변경과 삭제를 반영하고 모의 C 실행 파일을 빌드해 실행했다. `dev`에 테스트를 유지하면서 두 버전의 태그 아카이브에서 개발 전용 경로를 제외했다.
- 실제 ARG는 제품 소스가 추가된 후 Ubuntu 24.04에서 빌드와 초기 화면을 확인한다. 호스팅된 제출 검사는 첫 `main` 대상 릴리즈 PR에서 확인한다.
